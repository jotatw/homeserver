# HomeServer v2.0 — Release Hardening

> Documento de validação pré-release da versão 2.0.
>
> A v2.0 só poderá avançar para release quando os critérios obrigatórios deste documento forem validados.

## 1. Objetivo

Esta etapa tem como objetivo identificar, documentar, corrigir e validar problemas que possam comprometer:

- instalação;
- atualização;
- inicialização;
- operação;
- segurança;
- integridade dos dados;
- recuperação;
- experiência de um novo usuário;
- documentação;
- manutenção futura.

Durante o Hardening:

- não são adicionadas funcionalidades novas;
- problemas encontrados são registrados antes da correção;
- correções devem ser pequenas e rastreáveis;
- toda correção deve possuir reteste;
- nenhum resultado é considerado validado sem evidência.

## 2. Regra de Freeze

### Permitido

- correções de bugs;
- correções de segurança;
- correções de documentação;
- correções de testes;
- correções de CI/CD;
- melhorias necessárias para confiabilidade;
- ajustes de configuração necessários para instalação segura.

### Não permitido

- novas funcionalidades;
- novos serviços;
- novos endpoints sem necessidade de correção;
- mudanças arquiteturais não essenciais;
- redesign;
- alteração de escopo da v2.0.

Qualquer funcionalidade identificada durante esta etapa deve ser registrada no backlog para uma versão posterior.

## 3. Estados de validação

Cada item deve possuir exatamente um estado:

- `IDENTIFICADO`
- `DOCUMENTADO`
- `TESTE_PENDENTE`
- `FALHOU`
- `CORRIGINDO`
- `RETESTE`
- `VALIDADO`
- `BLOQUEADO`

Fluxo obrigatório:

```text
IDENTIFICADO
    ↓
DOCUMENTADO
    ↓
TESTE
    ↓
FALHOU
    ↓
CORREÇÃO
    ↓
RETESTE
    ↓
VALIDADO
```

## 4. Critérios de severidade

### CRÍTICO

Bloqueia a release.

Exemplos:

- instalação destrói dados;
- credenciais são expostas;
- autenticação pode ser contornada;
- usuário comum consegue executar operação administrativa;
- backup não pode ser recuperado;
- update deixa o servidor inutilizável;
- instalação produz configuração insegura por padrão.

### ALTO

Bloqueia a release caso não exista mitigação documentada.

Exemplos:

- serviço essencial não retorna após reboot;
- permissões permitem acesso indevido;
- instalação não é reproduzível;
- API possui operação administrativa sem proteção adequada;
- configuração secreta é gravada incorretamente.

### MÉDIO

Deve ser corrigido antes da release sempre que possível.

### BAIXO

Pode ser enviado para backlog se não afetar segurança ou confiabilidade.

## 6. Installer Audit

### 6.1 Instalação limpa

- [ ] clone funciona;
- [ ] `install.sh` inicia;
- [ ] dependências são verificadas;
- [ ] usuário é detectado/perguntado corretamente;
- [ ] rede é detectada corretamente;
- [x] nenhuma configuração pessoal do desenvolvedor é utilizada; *(corrigido — IP/usuário/senha removidos do código; validação em máquina limpa pendente)*
- [ ] diretórios são criados;
- [ ] permissões são corretas;
- [ ] Docker é instalado/configurado quando necessário;
- [ ] módulos são iniciados;
- [ ] API inicia;
- [ ] Homepage inicia;
- [ ] Caddy inicia;
- [ ] Health Check passa;
- [ ] acesso por `homeserver.local` funciona.

### 6.2 Dry Run

Regra: `--dry-run` não pode alterar o sistema.

- [x] não cria diretórios; *(corrigido e validado — `_create_dirs`/`_prepare_service_dirs` respeitam `--dry-run`)*
- [x] não altera permissões; *(corrigido — chown só fora do dry-run)*
- [ ] não altera `/etc`;
- [ ] não altera Samba;
- [ ] não altera UFW;
- [x] não cria `.env`; *(guard `DRY_RUN` em `_setup_api_env`)*
- [x] não gera credenciais; *(senha só fora do dry-run)*
- [ ] não inicia containers;
- [ ] não cria timers;
- [x] não pede credenciais; *(dry-run retorna antes do prompt)*
- [x] informa as ações que seriam executadas; *(mensagens `dry-run: …`)*

### 6.3 Non-interactive

- [x] nenhuma pergunta interativa; *(validado — non-interactive preservado)*
- [x] nenhuma senha padrão; *(corrigido — `usuario-exemplo` removido dos test scripts)*
- [x] nenhum usuário padrão pessoal; *(corrigido — `usuario` removido dos defaults)*
- [x] nenhuma rede padrão pessoal; *(corrigido — CORS/`HOMEPAGE_ALLOWED_HOSTS` via env; IP detectado)*
- [ ] valores obrigatórios ausentes causam erro;
- [ ] erro possui mensagem acionável;
- [ ] execução é determinística.

### 6.4 Idempotência

Executar:

```bash
sudo bash install.sh
sudo bash install.sh
```

Validar:

- [ ] não duplica configuração;
- [ ] não duplica shares;
- [ ] não recria credenciais desnecessariamente;
- [ ] não destrói dados;
- [ ] não cria containers duplicados;
- [ ] não duplica timers;
- [ ] estado final permanece válido.

## 16. Zero Knowledge Test

O teste final deve ser realizado por alguém que não participou da implementação.

A pessoa recebe somente:

- Debian;
- acesso ao repositório;
- acesso à rede;
- documentação pública.

Não recebe:

- explicações do desenvolvedor;
- comandos adicionais;
- configuração pronta;
- conhecimento da arquitetura;
- acesso ao código para descobrir como fazer.

Critério:

> A pessoa deve conseguir instalar, acessar e utilizar o HomeServer sem precisar programar ou consultar o desenvolvedor.

Resultado:

- [ ] PASS
- [ ] FAIL

## 17. Critério de aprovação

A v2.0 **NÃO PODE SER RELEASED** se existir:

- qualquer item `CRÍTICO` aberto;
- qualquer vulnerabilidade de autenticação/autorização não corrigida;
- instalação limpa quebrada;
- upgrade quebrado;
- perda de dados;
- reboot quebrado;
- backup não restaurável;
- Zero Knowledge Test falhando;
- Quality Gate vermelho.

Itens `ALTO` somente podem permanecer com:

1. mitigação documentada;
2. justificativa;
3. issue registrada;
4. decisão explícita de release.

## 18. Evidências
