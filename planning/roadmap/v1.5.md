# HomeServer v1.5 — Stabilization (Plano Oficial)

> **Filosofia**: não adicionar funcionalidade nova. Certificar a plataforma.
> **Identidade**: v1.4 → Experiência · **v1.5 → Qualidade** · v2.0 → Plataforma
> **Regra**: construção → consolidação → expansão (para toda a vida útil do projeto).

## Objetivo

Tornar o HomeServer sólido, consistente e seguro antes da v2.0.

A v1.5 não introduz novas capacidades. Ela:

- revisa código (Foundation, Infrastructure, Adapters, API);
- audita segurança e registra hipóteses;
- padroniza nomenclatura, configuração e logs;
- mede performance e cria histórico;
- revisa arquitetura e documentação;
- amplia testes (API, CLI, adapters, smoke, regression);
- congela a arquitetura principal.

## Decisões oficiais

### Nomenclatura (dois padrões por camada)

- **Foundation**: `hs_*` (`hs_fs_*`, `hs_cfg_*`, `hs_val_*`, `hs_out_*`, `hs_const_*`, `hs_registry_*`).
- **Infrastructure**: prefixo do módulo (`storage_*`, `users_*`, `devices_*`, `hardware_*`, `backup_*`, `scheduler_*`, `power_*`, `compose_*`, `service_*`).
- **Adapters**: `filebrowser_*`.
- **CLI**: `hs <comando> <subcomando>`.
- **Eliminar funções órfãs sem prefixo** (ex.: `copy_file`, `create_directory`, `directory_exists`, `file_exists`, `move_file` → `hs_fs_*`).

### API (pipeline único)

```
Request → Validação → Service → Resposta
```

- Respostas sempre `{"ok":true,"data":{}}` ou `{"ok":false,"error":"..."}`.
- Códigos HTTP corretos.
- Validação em todas as rotas, mesmo as sem parâmetros.
- Mensagens e logs padronizados.

## Sprints

### Sprint 1 — Code Review
- Foundation: convenções, comentários, exit codes, tratamento de erro.
- Infrastructure: checklist por módulo (storage, users, services, devices, hardware, backup, scheduler, power, compose) — responsabilidade única, validação, logs, retorno consistente.
- Adapters: FileBrowser — timeout, retry, mensagens, duplicação.
- API: validação + `ok/data` + `ok/error` + status HTTP + logs.
- **Dependency Review** → `planning/dependencies.md` (registrar versões; não atualizar "no escuro").

### Sprint 2 — Segurança
- Usuários: senha mínima, hash, validação, permissões.
- API: CORS, HTTPS, headers, rate limit, auth — registrar estado atual.
- Docker: privileged, volumes RW, secrets, usuários.
- Arquivos: permissões de `/srv`, `/storage`, `/backup`, `/config`, `/git`.
- **Threat Model** (LAN → API → CLI → Containers → Storage).
- **Security Assumptions** (LAN-only, admin único, sem auth externa, HTTPS interno).

### Sprint 3 — Consistência
- Nomenclatura: eliminar órfãs; atualizar CONTRIBUTING.
- CLI: verbos uniformes (`list/info/create/rm/password/verify/...`).
- Configuração: padrão de chaves (`enable` vs `enabled`, yaml/conf/env).
- Logs: formato `DATA MÓDULO NÍVEL MENSAGEM`.

### Sprint 4 — Performance
- Medir e registrar histórico em `planning/health/v1.5.md`.
- Metas: Homepage < 1s · API < 100ms · CLI < 300ms · boot/shutdown/update.

### Sprint 5 — Arquitetura (documental)
- Revisar README, API docs, ARCHITECTURE, VISION, PRINCIPLES, ROADMAP, backlog.
- **ADRs** em `docs/architecture/adr/`: auth, auto-update, religamento S3, nomenclatura, resposta da API, congelamento de arquitetura.

### Sprint 6 — Testes
- API (HTTP ok/data), CLI (`hs user`, `hs update`), Adapters (FileBrowser).
- **Regression tests** (bug corrigido → teste, para nunca voltar).
- **Smoke tests** (`scripts/smoke-test.sh`): `hs status` · Homepage abre · API responde · Storage responde · Users responde.
- Gate: `core/tests/run_ci.sh` (shellcheck + suite).

### Sprint 7 — Release
- **v1.5.0** — "HomeServer — Stable Foundation".
- CHANGELOG + tag + push github/gitea + `hs update apply` validado.
